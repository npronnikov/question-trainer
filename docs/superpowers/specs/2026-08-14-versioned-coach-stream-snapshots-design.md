# Версионированные снимки потокового ответа коуча

**Дата:** 2026-08-14  
**Статус:** согласовано

## Проблема

Ответ коуча иногда отображается с переставленными слогами и словами. Текущий
контракт передаёт текст как независимые SSE-дельты, а frontend безусловно
добавляет каждую дельту к уже показанному тексту.

Предыдущие исправления закрыли гонку между backlog и новой SSE-подпиской,
отфильтровали служебную фазу `commentary` и синхронизировали накопитель ответа.
Однако синхронизация накопителя не восстанавливает исходный порядок: sync API
ACP SDK отправляет каждое `session/update` в общий cached thread pool. Поток,
получивший более позднее уведомление, может первым захватить монитор накопителя.

Есть и вторая системная слабость. При повторном подключении EventSource сервер
воспроизводит все накопленные дельты, а клиент повторно дописывает их к локальному
тексту. У текущих событий нет версии или идентификатора, по которому можно
отбросить повтор либо задержанное событие.

## Цель

Сделать живой ответ коуча идемпотентным: повтор, задержка, переподключение или
пропуск промежуточного SSE-события не должны перемешивать либо дублировать текст.
Показанный и сохранённый ответы должны происходить из одного последовательного
накопителя.

## Требуемое поведение

- Видимые ACP-уведомления обрабатываются в порядке поступления из транспорта.
- UI получает полные снимки ответа, а не текстовые дельты.
- Каждый снимок содержит монотонно возрастающую версию.
- UI принимает только снимок с версией новее уже принятой и заменяет текст
  целиком.
- При повторной подписке сервер отправляет только последний актуальный снимок.
- Терминальное событие `done` содержит окончательные `version` и `text` и является
  авторитетным результатом для UI.
- Сохранённое сообщение совпадает с `text` из `done`.
- Служебная фаза `commentary` по-прежнему не попадает в пользовательский ответ.
- Обновление DOM выполняется не чаще одного раза за 60 миллисекунд.

## Архитектура

### Последовательная граница ACP

`AcpGateway` переходит с sync builder ACP-клиента на async builder. Все операции
инициализации, аутентификации, создания сессии, выбора модели и отправки prompt
по-прежнему вызываются последовательно с ожиданием результата.
Клиент закрывается в `finally`: сначала выполняется ограниченное по времени
graceful-завершение, затем освобождаются transport и внутренние scheduler.

Обработчик `session/update` возвращает синхронно завершающийся `Mono`: внутри него
фильтруется сообщение и обновляется накопитель. В отличие от sync consumer,
такой обработчик не отправляется SDK в `SYNC_HANDLER_SCHEDULER`. Он завершается во
время обработки текущего входящего уведомления, до обработки следующего
уведомления транспортом.

Накопитель имеет единственную обязанность: отфильтровать пользовательский текст,
добавить его к итоговому ответу и сообщить новое полное значение подписчику.
`AcpMessageFilter` сохраняет текущие правила: `commentary` скрывается,
`final_answer`, неизвестная фаза и сообщение без фазы принимаются.

### Состояние запуска

`RunStreamRegistry.StreamState` вместо списка всех дельт хранит:

- владельца запуска;
- последний полный текст;
- текущую версию;
- список активных emitter;
- терминальное состояние и терминальное событие.

Операция публикации снимка выполняется под монитором `StreamState`:

1. игнорирует публикацию после терминального события;
2. увеличивает версию;
3. заменяет сохранённый текст;
4. отправляет активным подписчикам событие `snapshot` с `{version, text}`.

При подписке под тем же монитором сервер сначала проверяет терминальное состояние.
Для завершённого запуска он отправляет только сохранённое авторитетное событие
`done` и завершает emitter. Для активного запуска он отправляет один последний
снимок, если тот существует, а затем регистрирует emitter для будущих событий.
Backlog промежуточных снимков не хранится и не воспроизводится.

### Ограничение частоты отображения

Надёжность протокола не зависит от частоты обновления. Сервер публикует новый
версионированный снимок при каждом принятом текстовом фрагменте. Frontend хранит
самый свежий принятый снимок и планирует отрисовку не чаще одного раза за
60 миллисекунд. Несколько событий в этом окне объединяются в одну перерисовку
Markdown.

Это не добавляет серверный планировщик, lifecycle которого пришлось бы отдельно
завершать и принудительно сбрасывать перед `done`. Сетевой объём остаётся
приемлемым для коротких коучинговых ответов, а финальное событие гарантирует
полную синхронизацию.

### Контракт SSE

Промежуточное событие:

```text
event: snapshot
data: {"version": 7, "text": "Полный текст ответа на текущий момент"}
```

Успешное терминальное событие:

```text
event: done
data: {
  "version": 8,
  "text": "Окончательный полный текст ответа",
  "source": "ACP",
  "messageId": "..."
}
```

Терминальная публикация всегда увеличивает версию на единицу, сохраняет
окончательный текст в состоянии запуска и отправляет его в `done`. Поэтому
`done.version` строго больше версии любого ранее отправленного снимка.

Ошибка без пользовательского текста:

```text
event: failure
data: {"message": "ACP-агент недоступен: ..."}
```

Старое событие `delta` удаляется одновременно из backend и frontend. Отдельный
переходный период не нужен, поскольку обе части поставляются из одного
репозитория.

## Frontend

Для каждого запущенного ответа frontend хранит:

- `acceptedVersion`, изначально `-1`;
- последний принятый полный `text`;
- идентификатор отложенной перерисовки;
- текущий `EventSource`.

На `snapshot` клиент проверяет типы полей. Снимок принимается, только если его
версия строго больше `acceptedVersion`. Принятый текст заменяет локальный текст
целиком. Отрисовка Markdown объединяется в окно около 60 миллисекунд.

На `done` клиент отменяет ожидающую перерисовку, закрывает EventSource, принимает
терминальные версию и текст без конкатенации, немедленно отображает их и добавляет
метку источника. `done.text` авторитетен даже тогда, когда промежуточный снимок
был пропущен.

Задержанное событие с меньшей или равной версией игнорируется. Повторная
подписка безопасна: сервер присылает последний снимок, а его применение является
заменой, а не добавлением.

## Завершение и ошибки

- При успешном ACP-ответе сообщение сначала сохраняется в базе, затем `done`
  отправляет тот же текст, версию, источник и идентификатор сообщения.
- При ошибке после получения части текста к накопленному ответу добавляется
  существующая пометка о разрыве. Этот окончательный частичный текст сохраняется
  с источником `ACP_PARTIAL` и целиком передаётся в `done`.
- При ошибке до первого пользовательского фрагмента сохраняется текущий fallback.
  Его текст публикуется как снимок и затем как `done` с источником `FALLBACK`.
- Если fallback отключён, отправляется `failure`; текст ответа не сохраняется.
- Публикации после `done` или `failure` игнорируются.
- Ошибка отправки одному emitter завершает только этот emitter; состояние запуска
  и остальные подписчики продолжают работу.

## Компоненты и границы

- `AcpGateway` управляет ACP lifecycle и гарантирует последовательную доставку
  уведомлений накопителю.
- `AcpResponseCollector` фильтрует и собирает единственный канонический текст.
- `ChatService` сохраняет ответ и переводит полный текст в события состояния
  запуска.
- `RunStreamRegistry` версионирует снимки, хранит только последнее состояние и
  управляет SSE-подписчиками.
- `frontend/app.js` применяет версии идемпотентно и ограничивает частоту
  перерисовки Markdown.

## Проверки

1. Интеграционный unit-тест ACP-адаптера передаёт несколько уведомлений через
   фактический async handler и подтверждает исходный порядок текста.
2. Фильтрация `commentary`, поддержка `final_answer` и сообщений без фазы остаются
   покрыты существующими тестами.
3. `RunStreamRegistry` увеличивает версию и отправляет полные снимки.
4. Новая подписка получает только последний снимок, а не историю снимков.
5. Публикация одновременно с подпиской не создаёт дублей и сохраняет
   монотонность версии.
6. `done` содержит окончательный текст и версию после всех снимков.
7. Публикация после терминального события игнорируется.
8. Frontend игнорирует повторную или меньшую версию, заменяет текст более новой
   версией и не конкатенирует снимки.
9. Frontend применяет `done.text`, даже если последняя промежуточная версия была
   пропущена.
10. Проверяются ветви `ACP_PARTIAL`, `FALLBACK` и `failure` без текста.
11. Проходят полные backend- и frontend-тесты, проверка синтаксиса JavaScript и
    `git diff --check`.

## Вне области изменения

- Визуальный редизайн страницы коуча, типографики или карточек сообщений.
- Отображение reasoning, tool calls или фазы `commentary`.
- Возобновление генерации после перезапуска backend.
- Долговременное хранение состояния незавершённых запусков.
- Изменение промпта коуча.
