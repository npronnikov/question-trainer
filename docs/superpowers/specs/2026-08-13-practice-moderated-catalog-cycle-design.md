# Модерируемый каталог и последовательная практика

## Цель

Режим «Практика» выдаёт пользователю только ситуации, которые администратор сгенерировал через ACP и опубликовал после модерации. Пользователь проходит ситуации последовательно по семи категориям и не может начать новый цикл до зачёта текущего.

Встроенные сценарии учебной программы остаются доступны в тренажёре распознавания категорий, но не считаются каталогом полного цикла и не выдаются в «Практике».

## Границы ролей

### Администратор

Администратор использует существующий раздел «Модерация» и кнопку генерации кандидатов. Только этот административный endpoint вызывает ACP.

Каждый ответ ACP сначала сохраняется как `scenario_candidate` и проходит существующую автоматическую проверку. Кандидат становится доступен в «Практике» только после ручной публикации. Автоматически отклонённые, отклонённые вручную и ожидающие проверки кандидаты пользователям не выдаются.

### Пользователь

Кнопки `Получить ситуацию`, `Новая ситуация` и `Следующая ситуация` никогда не вызывают ACP. Они запрашивают у backend следующую опубликованную ситуацию из модерируемого каталога.

Пользователь не выбирает категорию вручную. Параметр `targetCategory` удаляется из публичного создания assignment либо игнорируется с отказом, чтобы клиент не мог обойти серверный порядок.

## Порядок генерации ACP

Canonical-порядок категорий берётся из `category.sort_order`:

1. `INVERSION`
2. `HYPERBOLE`
3. `CROSS_DISCIPLINE`
4. `BACKCASTING`
5. `PROVOCATION`
6. `REFRAMING`
7. `SIMPLIFICATION`

Порядок глобален для очереди генерации. Первая сохранённая запись `scenario_candidate` получает первую категорию, вторая — вторую, седьмая — седьмую, восьмая — снова первую. При пакетной генерации сервер заранее вычисляет категорию для каждой позиции и передаёт ACP точный упорядоченный список.

Позиция следующей генерации вычисляется по уже сохранённым кандидатам. В последовательности учитываются все кандидаты независимо от результата модерации: `PENDING_REVIEW`, `AUTO_REJECTED`, `REJECTED` и `PUBLISHED`. Благодаря этому отклонение не изменяет категории уже созданных записей и не переиспользует их порядковые номера.

Новый отдельный prompt для административной генерации требует:

- вернуть ровно один JSON-массив без Markdown;
- вернуть столько объектов, сколько категорий передал сервер;
- сохранить порядок объектов;
- для каждого объекта установить `category` и `correctCategory` в переданное значение;
- соблюдать существующую схему `ScenarioDraft`, правила безопасности, длины и учебной однозначности;
- не копировать встроенные или уже сгенерированные ситуации.

Если ACP возвращает другую категорию, неверное количество или невалидный JSON, запрос не публикует материал напрямую. Ошибочный объект не становится доступным пользователям; применяются существующая ошибка генератора или автоматический отказ в зависимости от того, можно ли разобрать ответ по объектам.

Для текущей архитектуры с одним backend-процессом административные запросы генерации сериализуются, чтобы два одновременных запроса не получили одинаковую стартовую позицию.

## Персональная последовательность пользователя

Следующая категория пользователя вычисляется по числу его сохранённых `practice_assignment`:

`nextCategoryIndex = assignmentCount mod 7`

Таким образом, каждый пользователь независимо проходит категории `1…7`, затем снова `1…7`. Прогресс других пользователей на его последовательность не влияет.

Для вычисленной категории backend выбирает опубликованный moderated scenario, который ещё ни разу не выдавался этому пользователю. Один и тот же опубликованный сценарий можно выдавать разным пользователям, но одному пользователю он повторно не выдаётся.

Создание `practice_assignment` и пустого серверного черновика остаётся одной транзакцией. Assignment сохраняет снимок текста ситуации и категории, поэтому последующее изменение каталога не меняет уже начатый цикл.

## Блокировка незавершённого цикла

Перед созданием assignment backend проверяет все циклы пользователя. Новая ситуация разрешена только тогда, когда у пользователя нет ни одного незачтённого цикла.

Незавершёнными считаются:

- новый assignment или черновик без попытки;
- `EVALUATING`;
- `NEEDS_REVISION`;
- `UNVERIFIED`.

Только `PASSED` открывает следующую ситуацию. Проверка выполняется на сервере и не зависит от состояния интерфейса. При обходе UI backend возвращает конфликт с понятным кодом и сообщением.

Frontend после загрузки истории также блокирует кнопки получения ситуации, если существует незачтённый цикл. Он показывает пользователю этот цикл как действие для продолжения. После получения `PASSED` кнопка следующей ситуации становится доступна.

## Исчерпание каталога

Если для следующей категории нет опубликованной ситуации, которую пользователь ещё не проходил, assignment не создаётся. Backend возвращает отдельный доменный код исчерпания каталога, отличимый от блокировки незавершённым циклом.

Frontend показывает сообщение:

> Вы прошли все доступные ситуации. Дождитесь, пока администратор добавит новые.

Сообщение не обещает автоматическую генерацию и не вызывает ACP. История пользователя остаётся доступной. После публикации администратором новой ситуации требуемой категории пользователь может повторить запрос без сброса прогресса.

## Начальное состояние данных

В начальном каталоге полного цикла нет доступных ситуаций. При выборе assignment repository рассматривает только сценарии, опубликованные через `scenario_candidate`; встроенные записи таблицы `scenario` от миграции учебной программы исключаются этим условием.

Отдельно удалять встроенные сценарии из БД нельзя: они используются режимом распознавания категорий.

## API и интерфейс

Сохраняются существующие маршруты:

- `POST /api/admin/scenario-candidates/generate` — ACP-генерация только для администратора;
- approve/reject/edit endpoints модерации — существующий процесс публикации;
- `POST /api/practice/assignments` — выдача готового опубликованного материала без ACP;
- history, draft, attempt и revision endpoints — без изменения назначения.

Ответы `POST /api/practice/assignments` различают как минимум:

- незавершённый текущий цикл;
- отсутствие непройденного опубликованного сценария для следующей категории.

В интерфейсе администратора сохраняются выбор количества, модели, очередь и ручная модерация. В интерфейсе пользователя кнопка отображает только действие получения готовой ситуации и не содержит выбора модели или категории.

## Ошибки и согласованность

- Недоступность ACP влияет только на административную генерацию и не ломает выдачу уже опубликованных ситуаций.
- Ошибка генерации не создаёт assignment пользователя.
- Повторный быстрый клик блокируется frontend, а серверная транзакционная проверка не допускает два активных assignment.
- Конкурирующая выдача одного каталожного сценария разным пользователям допустима.
- Конкурирующая выдача одного сценария одному пользователю не должна создавать дубликат.
- Старые данные с несколькими незавершёнными циклами не удаляются; новая выдача блокируется до их завершения.

## Тестирование и критерии приёмки

Backend-тесты до реализации фиксируют:

- первый пакет ACP получает категории `1…7`, а восьмой объект — снова категорию `1`;
- следующий пакет продолжает порядок по сохранённым кандидатам, включая отклонённые;
- несовпадение категории ответа ACP не публикуется;
- только администратор может вызвать генерацию;
- пользовательский endpoint не вызывает `ScenarioGenerationGateway`;
- два пользователя начинают собственную последовательность с категории `1`;
- один пользователь получает категории `1…7`, а восьмой assignment — категорию `1`;
- следующий assignment запрещён для черновика, `EVALUATING`, `NEEDS_REVISION` и `UNVERIFIED`;
- следующий assignment разрешён после `PASSED`;
- пользователю не повторяется ранее выданный scenario;
- встроенные сценарии и неопубликованные кандидаты не выдаются;
- при исчерпании нужной категории возвращается отдельный доменный ответ;
- owner-only доступ к assignment и истории сохраняется.

Frontend-тесты фиксируют:

- кнопки получения ситуации заблокированы при незачтённом цикле;
- после `PASSED` доступно действие следующей ситуации;
- исчерпание показывает согласованный текст ожидания администратора;
- пользовательский код вызывает только `/practice/assignments`, но не ACP и не административную генерацию;
- административная генерация и модерация остаются role-gated.

Полная проверка включает backend test suite, frontend tests и сборку приложения.
