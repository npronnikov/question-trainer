# Потенциал идеи и динамика по категориям в «Практике»

## Цель

Раздел «Практика» должен показывать не только факт зачёта отдельного кейса, но и то, как со временем меняется качество идей пользователя в каждой из семи категорий мышления.

После каждой проверенной попытки пользователь получает четырёхосевую паутинку идеи. Оценки сохраняются вместе с попыткой. После прохождения повторных кругов категорий пользователь может по требованию открыть детерминированный график и сравнить первую, вторую, третью и последующие попытки в одной категории, например только в `INVERSION` или только в `PROVOCATION`.

Отдельного AI-отчёта по семи кейсам и отдельного циклового prompt нет. AI используется только в существующей оценке отдельной попытки; паутинки, группировка по циклам и графики строятся обычным серверным и клиентским кодом из сохранённых оценок.

## Термины и границы

- **Кейс** — один `practice_assignment` в конкретной категории.
- **Попытка** — один `practice_attempt` внутри кейса. Исправление создаёт новую попытку и не перезаписывает предыдущую.
- **Цикл** — семь последовательных кейсов пользователя в canonical-порядке категорий: `INVERSION`, `HYPERBOLE`, `CROSS_DISCIPLINE`, `BACKCASTING`, `PROVOCATION`, `REFRAMING`, `SIMPLIFICATION`.
- **Паутинка** — профиль одной проверенной попытки по четырём осям потенциала идеи.
- **Точка динамики** — оценки первой семантически проверенной попытки кейса. Исправления сохраняются в истории кейса, но не заменяют эту точку.

В scope входят оценка потенциала идеи, паутинка попытки, сохранение результатов, циклы и динамика внутри выбранной категории.

В scope не входят AI-отчёты по циклу, сравнение пользователей, рейтинги, streak-механики, изменение семи учебных категорий и автоматическая публикация практических ситуаций.

## Оценка потенциала идеи

Активная оценка попытки переводится на новый ресурс `practice-assessment-v3.md` и schema `practice-assessment-v3` с секцией `ideaPotential`. Она по-прежнему проверяет вопрос, связность обоснования, решение, попадание в категорию и силу вопроса, но дополнительно независимо оценивает четыре оси идеи. Legacy-ресурсы v1/v2 сохраняются только для чтения старой истории.

### Оси

1. **Сила идеи** (`impact`) — насколько существенно идея способна изменить результат ситуации, а не дать косметическое улучшение.
2. **Связь с вопросом** (`questionAlignment`) — отвечает ли решение именно на сформулированный вопрос и найденный в нём механизм.
3. **Дизрапт / оригинальность** (`disruption`) — насколько идея выходит за пределы очевидного и привычного решения в контексте ситуации.
4. **Реализуемость** (`feasibility`) — можно ли воплотить идею при ресурсах, ограничениях и обстоятельствах, явно заданных текущим кейсом.

Каждая ось оценивается отдельно целым числом `0..4`:

- `0` — критерий отсутствует или ответ прямо ему противоречит;
- `1` — слабое декларативное проявление без работающего механизма;
- `2` — правдоподобное, но ограниченное или недостаточно развитое проявление;
- `3` — сильное, конкретное и подтверждённое ответом проявление;
- `4` — исключительно сильное проявление в рамках условий данного кейса.

Модель обязана вернуть для каждой числовой оценки короткое доказательство, привязанное к тексту вопроса, обоснования или решения. Она не сравнивает пользователя с другими людьми и не использует внешние сведения, которых нет в ситуации и ответе.

### Недостаток контекста

Для `feasibility` разрешён статус `INSUFFICIENT_CONTEXT` со значением `score = null`, если кейс не содержит достаточных сведений о ресурсах или ограничениях. Недостаток контекста не превращается в нулевой балл.

Если хотя бы одна ось не оценена, общий потенциал идеи также равен `null`. Паутинка показывает известные оси и явно отмечает разрыв «Недостаточно данных». Такая попытка сохраняется, но не создаёт итоговую точку общего потенциала в графике. Отдельные оценённые оси могут отображаться в деталях попытки, но неполный профиль нельзя выдавать за сопоставимый общий результат.

### Общий показатель

Когда оценены все четыре оси, сервер вычисляет общий потенциал идеи как арифметическое среднее и округляет только для отображения до одного знака:

`overall = (impact + questionAlignment + disruption + feasibility) / 4`

Модель не возвращает и не вычисляет `overall`, чтобы итог всегда был детерминированным и проверяемым.

Оценка потенциала идеи носит диагностический характер. Она не меняет существующие серверные правила `PASSED`/`NEEDS_REVISION` и не расширяет список полей для обязательного исправления. Пользователь может получить зачёт с невысоким потенциалом идеи и увидеть это как следующую зону развития.

## Контракт оценки и хранение

Новая версия схемы ответа модели содержит структуру следующего смысла:

```json
{
  "ideaPotential": {
    "dimensions": [
      {"name": "impact", "status": "SCORED", "score": 3, "evidence": "..."},
      {"name": "questionAlignment", "status": "SCORED", "score": 4, "evidence": "..."},
      {"name": "disruption", "status": "SCORED", "score": 2, "evidence": "..."},
      {"name": "feasibility", "status": "SCORED", "score": 3, "evidence": "..."}
    ]
  }
}
```

Parser проверяет наличие ровно четырёх уникальных осей, допустимые статусы, диапазон числовых значений и правило `INSUFFICIENT_CONTEXT -> score = null`. Любое нарушение делает семантическую оценку `UNVERIFIED` по существующему безопасному пути; сервер не строит паутинку из частично разобранного или придуманного результата.

В `practice_assessment` сохраняются:

- JSON четырёх измерений со статусами и доказательствами;
- вычисленный `idea_potential_score`, nullable;
- существующие `prompt_key`, `prompt_version`, `schema_version`, `model_id` и `confidence` для аудита сопоставимости.

Каждая попытка получает собственный снимок оценки. Исправление создаёт новую запись и сохраняет предыдущую паутинку без изменений.

Старые assessment-записи остаются читаемыми: у них `ideaPotential = null`, и они не включаются в новую динамику. Исторические ответы не переоцениваются автоматически другой моделью или новой версией prompt.

## Порядок кейсов и циклы

У assignment должен быть устойчивый персональный порядковый номер. Для нового кейса сервер атомарно назначает следующий `sequenceNumber`; из него однозначно вычисляются:

- `cycleNumber = floor((sequenceNumber - 1) / 7) + 1`;
- `cyclePosition = ((sequenceNumber - 1) mod 7) + 1`;
- категория из canonical-порядка по `cyclePosition`.

Порядок фиксируется в assignment, а не пересчитывается из текущего количества строк при каждом чтении. Это защищает циклы от неоднозначности при одинаковых timestamps и упрощает группировку истории. Для существующих assignment номера мигрируются в порядке `created_at, id` отдельно для каждого владельца.

Цикл считается отвеченным для аналитики, когда у всех семи его кейсов существует хотя бы одна `VERIFIED` попытка. `UNVERIFIED` из-за технической ошибки или низкой уверенности модели не закрывает позицию цикла.

Первая `VERIFIED` попытка каждого кейса становится неизменяемой точкой долгосрочной динамики. Если первая проверенная попытка получила `NEEDS_REVISION`, именно её оценки всё равно показывают самостоятельный уровень пользователя. Последующие исправления доступны внутри кейса как локальная эволюция ответа, но не подменяют межцикловый рост.

## API и серверная агрегация

Существующий `AttemptView.assessment` расширяется `ideaPotential`:

- четыре dimensions;
- nullable `overallScore`;
- признак полноты профиля.

Отдельный owner-only endpoint `GET /api/practice/idea-progress` возвращает уже нормализованные сервером данные, а не заставляет frontend скачивать и объединять всю историю попыток. Ответ содержит:

- номер последнего начатого и последнего отвеченного цикла;
- состояние доступности сравнения;
- семь категорий в canonical-порядке;
- для каждой категории список точек по `cycleNumber`;
- в каждой точке assignment/attempt identifiers, четыре оси, nullable overall и дату;
- причины пропусков: цикл не отвечен, assessment `UNVERIFIED`, старый schema или неполная реализуемость.

Сервер выбирает для каждой пары `(owner, assignment)` первую `VERIFIED` попытку. Frontend не решает, какая revision является первой или сопоставимой.

Агрегация не вызывает модель. Повторные запросы к графику читают только сохранённые оценки.

## Интерфейс

### Паутинка после попытки

После терминальной проверенной попытки текущий feedback дополняется паутинкой с четырьмя подписанными осями и общей оценкой `0..4`, если профиль полный. Рядом или под графиком выводятся четыре доказательства модели. Цвет не является единственным носителем значения: у каждой оси есть подпись и число.

При `INSUFFICIENT_CONTEXT` соответствующая ось не рисуется как ноль. Она имеет разрыв/пунктир и подпись «Недостаточно данных»; общий показатель скрыт. Это состояние не маскируется под низкий результат.

В timeline кейса каждая проверенная попытка сохраняет доступ к своей паутинке. Текущая попытка раскрыта, предыдущие можно открыть по требованию. Так пользователь видит локальное изменение после исправления, не смешивая его с долгосрочной динамикой.

### Экран динамики

В «Практике» появляется действие «Динамика идей». Оно доступно всегда, но честно объясняет объём данных:

- до первого полного отвеченного цикла — сколько категорий осталось;
- после 7 кейсов — первый набор сохранён, сравнение появится после следующего полного цикла;
- после 14 кейсов — доступно сравнение циклов;
- после 21 и более кейсов — линия получает третью и последующие точки.

Пользователь выбирает одну категорию. На графике по оси X расположены номера циклов, по оси Y — шкала `0..4`. По умолчанию показывается линия общего потенциала для первой, второй, третьей и последующих попыток в этой категории. Переключатель измерения заменяет её одной из четырёх осей, чтобы график оставался читаемым и не превращался в пять пересекающихся линий.

Нажатие на точку раскрывает исходный кейс, точную паутинку первой проверенной попытки и доказательства четырёх оценок. Пропущенная или несопоставимая точка отображается разрывом с объяснением, а не соединяется выдуманной линией.

### Визуальный характер

Интерфейс продолжает существующий мир «исследовательского журнала»: бумажные поверхности, чернила, кислотный акцент для доказанного изменения, фиолетовый для выбранной категории и оранжевый для зоны развития. Подписи и доказательства важнее декоративных карточек.

Фирменный элемент — переход от паутинки конкретной идеи к линии одной категории во времени. Это заменяет типовые KPI-карточки, streak и общий обезличенный рейтинг.

## Состояния и ошибки

- `EVALUATING` показывает существующее состояние ожидания без пустой паутинки.
- `UNVERIFIED` не показывает чисел и не добавляет точку; повторная проверка остаётся доступной.
- Неполный feasibility-профиль сохраняется и объясняется, но не получает overall.
- Старые попытки без новой схемы отображаются без паутинки с нейтральной пометкой «Оценка потенциала ещё не выполнялась».
- Ошибка endpoint динамики не ломает историю и форму практики; экран показывает локальную ошибку и действие повторной загрузки.
- Пустая категория и незавершённый цикл не интерполируются.
- При разных prompt/model версиях внутри schema v3 точка сохраняет audit metadata и остаётся в динамике. Все legacy-схемы без четырёх осей исключаются из динамики по явному правилу, а не по эвристике модели.

## Доступность

- Паутинка имеет текстовую альтернативу со всеми четырьмя значениями и статусами.
- Точки линии доступны с клавиатуры и имеют accessible name с категорией, циклом, значением и датой.
- Информация о росте, пропуске и недостатке данных не зависит только от цвета.
- На узком экране график сохраняет оси и подписи, а доказательства переходят под него без горизонтального скролла страницы.
- При `prefers-reduced-motion` переход между категориями и измерениями выполняется без анимированного движения линии.

## Тестирование и критерии приёмки

### Backend

- parser принимает ровно четыре корректные оси `0..4` и отклоняет дубликаты, пропуски, неизвестные имена и выход за диапазон;
- `INSUFFICIENT_CONTEXT` допустим только для feasibility и только с `score = null`;
- overall вычисляет сервер и не доверяет значению модели;
- idea potential не меняет существующее решение `PASSED`/`NEEDS_REVISION`;
- каждая revision сохраняет отдельный профиль, не перезаписывая parent attempt;
- динамика выбирает первую `VERIFIED`, а не последнюю или первую `UNVERIFIED` попытку кейса;
- assignment получает устойчивые `sequenceNumber`, `cycleNumber` и `cyclePosition` при конкурентном создании;
- категории каждого цикла соответствуют canonical-порядку;
- сравнение owner-only и не раскрывает чужие assignment/attempt;
- старые schema и неполные profiles дают объяснимые gaps, а не нули;
- чтение динамики не вызывает assessment gateway.

### Frontend

- терминальная проверенная попытка отображает четыре оси, значения и доказательства;
- incomplete feasibility показывает разрыв и не показывает overall;
- timeline позволяет открыть паутинки нескольких attempts одного кейса;
- до семи отвеченных кейсов показывается прогресс заполнения первого цикла;
- после первого цикла интерфейс сообщает, что для динамики нужен второй;
- после второго цикла выбор категории показывает две сопоставимые точки;
- третий цикл добавляет третью точку, не меняя предыдущие;
- переключатель overall/axis обновляет одну линию и accessible summary;
- click/keyboard activation точки открывает правильный case и первую verified attempt;
- loading, empty, unverified, legacy и request-error состояния не выдают фиктивные оценки.

### Полная проверка

Полная проверка включает migration tests, parser/service/repository/controller tests, frontend unit tests и browser-проверку desktop/mobile для полной паутинки, неполной реализуемости, двух циклов одной категории, gaps и истории revisions.

## Принятые продуктовые решения

- Оцениваются четыре независимые оси по шкале `0..4`, а не четыре бинарных признака.
- Паутинка относится к одной попытке одного кейса; её оси не являются семью категориями.
- Семь категорий образуют цикл только для временной группировки.
- Динамика сравнивает одну и ту же категорию между циклами.
- Долгосрочная точка берётся из первой `VERIFIED` попытки кейса.
- Все revision-паутинки сохраняются внутри кейса.
- Недостаток контекста реализуемости не превращается в ноль.
- Отдельного AI-отчёта, циклового prompt и модельного вызова при открытии графика нет.
