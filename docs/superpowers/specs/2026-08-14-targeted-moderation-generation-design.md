# Раздельная генерация кейсов в модерации

## Цель

Разделить административную генерацию материалов для двух учебных режимов. Практика должна получать ситуацию, в которой пользователь самостоятельно формулирует вопрос, ответ, рассуждение и решение. Тренажёр должен получать полную карточку распознавания техники с готовым вопросом и вариантами ответа.

Одновременно интерфейс модерации должен создавать ровно один кандидат за запуск, переиспользовать существующий выбор модели и усилия, показывать в очереди первые 50 символов ситуации и очищать редактор после публикации.

## Назначение материалов

В `scenario_candidate` и `scenario` появляется обязательное назначение материала:

- `PRACTICE` — ситуация для полного цикла практики;
- `TRAINER` — карточка для тренажёра распознавания.

Все существующие кандидаты и сценарии мигрируют в `TRAINER`. Поэтому после миграции практика не выдаёт старые материалы и остаётся без доступных ситуаций, пока администратор не сгенерирует и не опубликует новый `PRACTICE`-кандидат.

`PracticeRepository` выбирает только опубликованные сценарии с назначением `PRACTICE`. Репозитории тренажёра выбирают только `TRAINER`. Это исключает попадание неполной практической ситуации в карточки распознавания.

## Серверный цикл категорий

Backend сохраняет canonical-порядок категорий из `category.sort_order` и ведёт независимую позицию генерации для каждого назначения. Генерация тренажёрного кандидата не сдвигает следующую категорию практики и наоборот.

Для каждого запроса backend:

1. блокирует последовательность генерации;
2. находит число уже сохранённых кандидатов выбранного назначения;
3. вычисляет следующую категорию по модулю количества категорий;
4. подставляет категорию в prompt;
5. принимает результат ACP и сохраняет категорию из серверного решения, не позволяя модели выбирать или изменять её.

Каждый запрос создаёт ровно одного кандидата. Параметр количества удаляется из клиентского и серверного контракта.

## Генерация для практики

Отдельный prompt получает явную canonical-категорию и требует создать ситуацию именно для отработки этой техники. Ответ ACP содержит только:

```json
{
  "domain": "ПРОДУКТ",
  "situation": "Реалистичная ситуация для самостоятельной работы",
  "hint": "Направление размышления без раскрытия техники"
}
```

ACP не возвращает категорию, готовый вопрос, варианты ответа, объяснение или рассуждение. Backend дополняет результат заранее выбранной категорией и сохраняет поля тренажёра пустыми.

Автоматическая проверка практического кандидата валидирует:

- допустимую серверную категорию;
- длину домена, ситуации и подсказки;
- безопасность текста;
- отсутствие прямого названия или очевидного раскрытия категории в подсказке;
- отсутствие близкого дубликата ситуации.

При публикации сценарий сохраняет категорию, домен, ситуацию и подсказку без вариантов ответа. Миграция добавляет в `scenario` поле `hint_text` и разрешает `NULL` для `difficulty`, `question_text` и `explanation_text`. Для практического сценария эти три поля остаются `NULL`; фиктивный тренажёрный контент не создаётся.

## Генерация для тренажёра

Существующий полный prompt сохраняется для `TRAINER` и получает выбранную сервером категорию. ACP возвращает полную `ScenarioDraft`-карточку: категорию, сложность, домен, ситуацию, вопрос, подсказку, четыре варианта, правильную категорию, объяснение и при необходимости контраст.

Backend продолжает проверять совпадение возвращённой категории с запрошенной и применяет текущий полный автофильтр. После публикации карточка доступна только тренажёру.

## API

`POST /api/admin/scenario-candidates/generate` принимает:

```json
{
  "target": "PRACTICE",
  "model": "gpt-5.6-terra[high]"
}
```

`target` обязателен и допускает `PRACTICE` или `TRAINER`. `model` остаётся необязательным и использует текущую серверную модель по умолчанию. Число кандидатов не входит в контракт: сервис всегда генерирует один, даже если старый клиент дополнительно передаст неизвестное поле `count`.

Ответ остаётся списком из одного `CandidateView`, чтобы сохранить форму существующего клиентского потока. `CandidateView` дополнительно возвращает назначение кандидата.

Неизвестное назначение или модель возвращает `400`. Некорректный ответ ACP или нарушение схемы возвращает `502`; кандидат при этом не создаётся.

Редактирование не меняет назначение кандидата. Для практики изменяются только домен, ситуация и подсказка; категория показывается как неизменяемое серверное значение. Для тренажёра доступна полная существующая форма.

## Интерфейс модерации

Поле количества удаляется. В шапке появляются:

- переиспользованный компонент выбора модели и усилия из режима практики;
- кнопка `Сгенерировать для практики`;
- кнопка `Сгенерировать для тренажёра`.

Обе кнопки используют выбранный raw model identifier, включая суффикс усилия, и отправляют соответствующий `target`. Пока запрос выполняется, обе кнопки заблокированы, чтобы не запускать конкурирующие генерации из одной вкладки.

После генерации интерфейс переключается на статус `PENDING_REVIEW`, обновляет очередь и сообщает результат. Строка кандидата показывает назначение, категорию/сложность и первые 50 Unicode-символов ситуации. Если ситуация короче, она показывается полностью; дополнительные символы и отдельное многоточие не добавляются.

Практический редактор показывает неизменяемую категорию, домен, ситуацию и подсказку. Тренажёрный редактор показывает текущую полную форму. После успешной публикации `selectedCandidate` сбрасывается, список обновляется, а правая панель всегда перерисовывается в пустое состояние `Выберите кандидат в очереди.`

## Подсказка в практике

`hint` опубликованного практического сценария копируется в новое поле `practice_assignment.hint_text` как снимок вместе с доменом и ситуацией. Последующее изменение каталога не меняет уже начатую практику.

API assignment возвращает подсказку. В рабочей форме режима `Практика` рядом с ситуацией находится кнопка `Показать подсказку`. Текст подсказки изначально отсутствует из визуального потока и скрыт от assistive technology. После раскрытия кнопка меняется на `Скрыть подсказку`. При повторном открытии сохранённого цикла локальное состояние сбрасывается, поэтому подсказка снова скрыта.

## Согласованность и ошибки

- Генерация и вычисление следующей категории выполняются в одной транзакции с существующей блокировкой последовательности.
- Счётчик цикла учитывает кандидатов любого статуса, но только того же назначения.
- Автоматически и вручную отклонённые кандидаты продолжают занимать свою позицию цикла.
- Ошибка генерации не сдвигает цикл, потому что несохранённый кандидат не учитывается.
- Публикация остаётся оптимистически защищённой версией кандидата и создаёт сценарий ровно один раз.
- Назначение нельзя изменить через edit endpoint.
- Пользовательские endpoints не вызывают ACP.

## Тестирование

Backend-тесты фиксируют:

- запрос генерации создаёт ровно одного кандидата независимо от старого поля `count`;
- `PRACTICE` и `TRAINER` используют независимые циклы категорий;
- практический prompt содержит выбранную сервером категорию;
- практический ответ ACP содержит только домен, ситуацию и подсказку, а сохранённая категория берётся с сервера;
- практический автофильтр отклоняет раскрывающую категорию подсказку;
- тренажёр сохраняет полный прежний контракт и проверки;
- старые данные мигрируют в `TRAINER`;
- practice assignment выбирает только `PRACTICE`, а trainer issuance — только `TRAINER`;
- assignment сохраняет и возвращает снимок подсказки;
- approve публикует каждый тип материала ровно один раз.

Frontend-тесты фиксируют:

- отсутствие поля количества;
- наличие двух кнопок и переиспользованного model picker;
- передачу `target` и выбранной модели;
- блокировку обеих кнопок во время генерации;
- первые 50 символов ситуации в строке очереди;
- разные формы кандидатов;
- очистку правой панели после approve;
- скрытую по умолчанию подсказку практики и переключение её видимости.

Финальная проверка включает полный frontend test suite, backend test suite и сборку приложения.
