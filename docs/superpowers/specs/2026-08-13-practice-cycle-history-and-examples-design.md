# История полного цикла и серверные примеры практики

## Цель и границы

Расширить маршрут `#practice`, чтобы пользователь мог вернуться к любому ранее начатому полному циклу, увидеть всю историю попыток и рекомендаций модели и продолжить незавершённое исправление без потери введённого текста.

На стартовом экране практики до открытия или создания цикла показывать один случайный заполненный пример полного цикла. И циклы, и черновики, и примеры хранятся только на сервере.

В scope входят backend API, миграция базы, серверное автосохранение и интерфейс `#practice`. Чат коуча, алгоритм оценки, управление примерами из интерфейса администратора и синхронизация текущего выделения между устройствами не меняются.

## Интерфейс

### Левая колонка

Вместо статического описания «Полный цикл» левая колонка маршрута практики содержит:

- заголовок `Полный цикл`;
- кнопку создания новой ситуации;
- список всех циклов текущего пользователя, отсортированный по времени последней активности;
- для каждого цикла: методику, короткий фрагмент ситуации, статус, количество попыток и дату последней активности;
- выделение выбранного цикла.

Один цикл соответствует одной `practice_assignment`. Последующие исправления являются попытками этого же цикла и не создают отдельные строки в списке.

Статусы списка отображаются пользовательскими формулировками:

- выданная ситуация или сохранённый текст без отправки — `Черновик`;
- `EVALUATING` — `Оценивается`;
- `PASSED` — `Зачёт`;
- `NEEDS_REVISION` — `Нужна корректировка`;
- `UNVERIFIED` — `Не проверено`.

Пустая история показывает короткое сообщение без искусственно созданного цикла. Ошибка загрузки истории отображается в колонке и не блокирует стартовый пример.

### Стартовый экран справа

При каждом входе на `#practice` без выбранного цикла frontend запрашивает `GET /api/practice/examples/random`. Backend выбирает любой опубликованный пример случайно; повтор предыдущего примера разрешён.

Экран показывает:

- название методики и учебную ситуацию;
- четыре заполненных шага: вопрос, ответ, рассуждение, решение;
- рекомендацию модели;
- основное действие `Получить ситуацию`.

В базе находится ровно по одному начальному примеру для каждой из семи методик: `INVERSION`, `HYPERBOLE`, `CROSS_DISCIPLINE`, `BACKCASTING`, `PROVOCATION`, `REFRAMING`, `SIMPLIFICATION`. Примеры являются серверным учебным контентом, а не пользовательской историей.

### Выбранный цикл справа

Клик по строке истории загружает цикл и заменяет стартовый пример полным содержанием выбранного цикла:

1. Исходная ситуация и ориентир методики.
2. Хронологическая лента всех отправленных попыток.
3. В каждой попытке — вопрос, ответ, рассуждение и решение пользователя.
4. После завершённой попытки — сохранённая серверная оценка и рекомендация модели, включая сильные стороны и приоритетную корректировку.
5. Внизу — актуальный редактор или финальное действие.

Для `PASSED` цикл доступен только для чтения. Для `NEEDS_REVISION` он сразу открывается в рабочем режиме: поля последней попытки заполнены сохранёнными значениями, а редактировать можно поля из `fieldsToRevise`. Отдельная кнопка «Продолжить исправление» не требуется. Для `EVALUATING` интерфейс продолжает опрос статуса. Для `UNVERIFIED` сохраняется существующее объяснение отсутствия оценки.

Кнопка новой ситуации создаёт новый цикл, немедленно добавляет его в историю и открывает редактор. Возврат на стартовый экран выполняется отдельным действием в заголовке списка или снятием выбора; он не удаляет цикл.

## Серверная модель данных

### Существующие сущности

`practice_assignment` остаётся корнем цикла, `practice_attempt` — неизменяемой пользовательской попыткой, `practice_assessment` — неизменяемым ответом оценки. Это уже сохраняет отправленные вопросы, ответы, рассуждения, решения и рекомендации модели.

### Черновик

Новая таблица `practice_draft` хранит один актуальный черновик на цикл:

- `assignment_id` — первичный ключ и ссылка на `practice_assignment` с каскадным удалением;
- `owner_id` — владелец, используемый для явной проверки доступа;
- `base_attempt_id` — nullable-ссылка на попытку, относительно которой готовится исправление;
- `question_text`, `answer_text`, `reasoning_text`, `solution_text` — текущие значения, допускающие пустые строки;
- `updated_at`.

При создании assignment сервер создаёт пустой draft. Upsert черновика принимает все четыре текущих поля и `baseAttemptId`, проверяет владельца и размер каждого поля. Семантические минимумы применяются только при отправке на оценку.

После успешного создания попытки draft удаляется. Если оценка возвращает `NEEDS_REVISION`, detail API строит начальное состояние редактора из последней попытки даже до следующего автосохранения. Первое изменение создаёт новый draft с `baseAttemptId` этой попытки.

### Учебные примеры

Новая таблица `practice_example` хранит:

- UUID `id`;
- уникальный `category_code` со ссылкой на `category`;
- `domain_text`, `situation_text`;
- `question_text`, `answer_text`, `reasoning_text`, `solution_text`;
- `recommendation_text`;
- `published` и `created_at`.

Миграция создаёт таблицу и семь опубликованных записей — по одной на каждую методику. Ограничение уникальности по `category_code` закрепляет правило «один пример на методику» для текущего scope.

## API

### История циклов

`GET /api/practice/cycles` возвращает owner-only список summary:

- `assignmentId`, `targetCategory`, `domain`, `situation`;
- вычисленный `status`;
- `attemptCount`;
- `createdAt`, `updatedAt`.

`updatedAt` — максимум из времени assignment, последней попытки и черновика. Статус берётся из последней попытки, а при наличии draft поверх терминального результата становится `DRAFT`, кроме фонового `EVALUATING`.

`GET /api/practice/cycles/{assignmentId}` возвращает:

- assignment screen model;
- все попытки в порядке `attemptNumber`, каждая с assessment;
- nullable draft;
- editor model: исходные значения, редактируемые поля и базовая попытка.

Оба endpoint возвращают только данные текущего пользователя. Чужой UUID отвечает `404`, как существующие practice endpoints.

### Автосохранение

`PUT /api/practice/cycles/{assignmentId}/draft` принимает `baseAttemptId` и четыре поля. Повторный одинаковый запрос безопасен. Ответ возвращает сохранённый draft и `updatedAt`.

Frontend отправляет autosave с debounce после ввода, показывает состояния `Сохраняем…`, `Сохранено`, `Не удалось сохранить` и повторяет сохранение после следующего изменения. Перед отправкой попытки он отменяет таймер и дожидается актуального сохранения, затем использует значения формы для существующего submit/revision endpoint.

### Случайный пример

`GET /api/practice/examples/random` возвращает один случайный опубликованный пример вместе с кодом и названием методики. Endpoint не принимает историю показов и не гарантирует отсутствие повторов.

Если опубликованных примеров нет, endpoint отвечает `404`; frontend оставляет понятное описание четырёх шагов и кнопку начала практики без заполненного примера.

## Потоки состояния

### Вход на маршрут

1. Frontend параллельно загружает историю и случайный пример.
2. Справа остаётся стартовый экран, даже если история не пуста.
3. Выбор истории загружает detail cycle и делает его текущим.
4. Повторный вход на маршрут в рамках одной страницы сохраняет текущее выделение; полная перезагрузка возвращает стартовый экран и новый случайный ответ backend.

### Новый цикл

1. `POST /api/practice/assignments` создаёт assignment и пустой draft.
2. Frontend добавляет summary в начало списка и открывает detail.
3. Ввод автоматически сохраняется через draft endpoint.
4. Submit создаёт первую попытку и удаляет draft.
5. После оценки detail и summary обновляются из серверного состояния.

### Исправление

1. При открытии `NEEDS_REVISION` сервер возвращает editor model на основе последней попытки.
2. Разрешены только `fieldsToRevise`; остальные шаги видны, но заблокированы.
3. Изменение сохраняет draft с `baseAttemptId`.
4. Submit revision создаёт новую неизменяемую попытку, удаляет draft и добавляет пару «попытка — рекомендация» в ленту.

## Доступность и адаптивность

- Список циклов размечается как навигационный список кнопок; выбранная строка имеет `aria-current`.
- Статусы автосохранения и оценки используют неблокирующие live-region.
- Хронология сохраняет смысловой порядок и заголовки уровней, а не полагается только на цвет.
- На узком экране левая колонка становится горизонтальной или раскрываемой историей над содержанием; все циклы остаются доступны с клавиатуры.
- Скрытые стартовый экран и cycle detail исключаются из фокуса через существующую схему `is-hidden`/`inert`.

## Ошибки и согласованность

- Ошибка autosave не уничтожает текст в DOM и не запрещает повторную отправку; пользователь видит, что черновик ещё не подтверждён сервером.
- Устаревшие ответы history/detail игнорируются с sequence token, чтобы быстрый выбор разных циклов не показывал чужое предыдущее состояние.
- Backend проверяет, что `baseAttemptId` принадлежит тому же assignment и является последней доступной для исправления попыткой.
- Submit/revision и удаление draft выполняются транзакционно после создания попытки.
- История строится из серверных данных и не использует `localStorage` или IndexedDB.

## Тестирование и критерии приёмки

Backend tests до реализации должны зафиксировать:

- owner-only history и detail;
- группировку нескольких revision attempts в один цикл;
- сортировку по последней активности;
- создание, обновление и восстановление draft;
- запрет чужого assignment/base attempt;
- удаление draft после принятой submit/revision;
- случайный example endpoint возвращает только опубликованную запись;
- миграция содержит ровно семь примеров и по одному на каждый category code.

Frontend tests до реализации должны зафиксировать:

- список циклов в левой колонке и выбранное состояние;
- серверные endpoints history, detail, draft и random example;
- заполненный пример на стартовом экране;
- debounce autosave и явный статус сохранения;
- восстановление и немедленное редактирование `NEEDS_REVISION`;
- отображение всей цепочки попыток и рекомендаций;
- отсутствие клиентского хранилища practice history/example.

Итоговая проверка включает frontend tests и syntax check, полный `mvn test`, а также browser-проверку desktop/mobile: стартовый пример, новый draft, reload-восстановление, revision flow, смена выбранных циклов и состояния ошибок.
