# Логи ACP и управление циклами практики

## Цель

Сделать взаимодействия backend с ACP Codex наблюдаемыми в стандартном серверном журнале, исправить доступ к подсказке и повторному прохождению практики, разрешить пользователю начинать новую ситуацию до завершения предыдущей и дать администратору безопасный способ удалить все пользовательские циклы практики.

## Логи взаимодействия с ACP

Все вызовы ACP проходят через `AcpGateway`, поэтому журналирование выполняется на этой границе и автоматически покрывает коуча, оценку практики и генерацию материалов для модерации.

Для каждого вызова создаётся уникальный `interactionId`. На уровне `INFO` backend пишет:

- начало взаимодействия: `interactionId`, выбранную модель и полный prompt;
- успешное завершение: тот же `interactionId`, длительность в миллисекундах и полный собранный текст ответа.

При исключении backend пишет запись уровня `ERROR` с `interactionId`, длительностью и stack trace. Если ACP завершил ход без текста, это также считается ошибкой и журналируется через тот же путь.

Переменные окружения, API-ключи, настройки аутентификации и содержимое передаваемых credentials в журнал не попадают. Ответ логируется один раз после завершения, а не отдельной записью на каждый потоковый chunk.

## Удаление существующих циклов

Новая Flyway-миграция один раз удаляет все существующие пользовательские циклы практики вместе с полной историей. Удаление выполняется в порядке внешних ключей:

1. `practice_assessment` для попыток удаляемых назначений;
2. `practice_attempt`;
3. `practice_draft`;
4. `practice_assignment`.

Каталог опубликованных сценариев, кандидаты модерации, категории, примеры и данные тренажёра не удаляются. После миграции пользователи начинают историю практики заново.

## Административная очистка

Backend предоставляет `DELETE /api/admin/practice/cycles`. Доступ разрешён только пользователю с ролью `ADMIN` существующими правилами `/api/admin/**` и дополнительно проверяется текущим механизмом аутентификации контроллера.

Операция транзакционно удаляет те же четыре набора данных, что и миграция, и возвращает количество удалённых циклов. Повторный вызов на пустой базе успешен и возвращает `0`.

В разделе модерации появляется кнопка `Удалить все циклы практики`. Она видна только администратору, открывает явное подтверждение с предупреждением о безвозвратном удалении ответов и истории всех пользователей и блокируется на время запроса. После успеха интерфейс показывает количество удалённых циклов. При ошибке диалог остаётся безопасно закрытым, а ошибка показывается существующим toast-механизмом.

## Подсказка в практике

После очистки старых назначений новые циклы создаются только из опубликованных `PRACTICE`-сценариев, где подсказка проверена модерацией и копируется в `practice_assignment.hint_text`.

В открытой ситуации кнопка `Показать подсказку` отображается рядом с текстом ситуации. Сама подсказка по-прежнему скрыта до действия пользователя и снова скрывается при повторном открытии цикла. После раскрытия кнопка меняется на `Скрыть подсказку`.

Если повреждённые или вручную созданные данные всё же не содержат подсказку, интерфейс не показывает пустой disclosure и не ломает остальную форму.

## Явная форма исправления

Для результата `NEEDS_REVISION` блок обратной связи располагается перед формой редактирования. Форма получает заметный заголовок `Исправление попытки N` и краткое указание, какие шаги нужно изменить.

Только поля из серверного `fieldsToRevise` доступны для редактирования; остальные ответы остаются видимыми, но заблокированными. Поля для исправления сохраняют визуальное выделение. Кнопка в обратной связи называется `Перейти к исправлению` и прокручивает страницу к первому редактируемому полю. Submit-кнопка формы называется `Отправить исправление` и использует существующий endpoint revisions.

При повторном открытии незавершённого цикла состояние редактора восстанавливается из серверного draft. Валидация применяется только к полям, отмеченным сервером для исправления, а ошибка отсутствия фактических изменений показывается рядом с формой.

## Несколько незавершённых ситуаций

`PracticeAssignmentService` больше не отклоняет создание назначения из-за другого цикла со статусом `DRAFT`, `EVALUATING`, `NEEDS_REVISION` или `UNVERIFIED`. Блокировка пользователя на время выдачи сохраняется, чтобы два одновременных запроса не получили одну позицию последовательности.

Выбор следующей категории продолжает опираться на число уже выданных назначений. Один и тот же опубликованный сценарий не выдаётся пользователю повторно. Если подходящих новых сценариев нет, сервер по-прежнему возвращает `PRACTICE_CATALOG_EXHAUSTED`.

Frontend не ищет незавершённый цикл для блокировки кнопок. Кнопки получения новой ситуации отключаются только на время активного запроса. Все незавершённые циклы остаются в колонке `Полный цикл`, и пользователь может вернуться к любому из них.

## Ошибки и конкурентность

- ACP-ошибка одновременно фиксируется в журнале и продолжает использовать существующую прикладную обработку fallback/`UNVERIFIED`.
- Очистка циклов выполняется одной транзакцией; частично удалённая история невозможна.
- Создание назначения и административная очистка сериализуются средствами транзакций базы. После успешной очистки открытая вкладка пользователя может содержать устаревший assignment; следующий запрос вернёт `404`, после чего обновление списка покажет пустую историю.
- Пока оценка текущей попытки отправляется, глобальная защита от повторной отправки сохраняется. После завершения запроса пользователь может получить другую ситуацию независимо от результата оценки.

## Тестирование

Backend-тесты фиксируют:

- `AcpGateway` пишет полный запрос и полный успешный ответ с одним `interactionId`;
- исключение и пустой ответ журналируются как ошибки со stack trace;
- административный endpoint недоступен обычному пользователю;
- очистка удаляет assignments, drafts, attempts и assessments, не затрагивая сценарии;
- повторная очистка возвращает ноль;
- новое назначение можно получить при существующих `DRAFT`, `EVALUATING`, `NEEDS_REVISION` и `UNVERIFIED` циклах;
- последовательность категорий и запрет повторной выдачи сценария сохраняются.

Frontend-тесты фиксируют:

- admin-кнопку очистки и обязательное подтверждение;
- запрос `DELETE /api/admin/practice/cycles` и сообщение с количеством удалённых циклов;
- отсутствие клиентской блокировки новой ситуации незавершённым циклом;
- видимую кнопку подсказки для назначения с `hint` и скрытый текст до раскрытия;
- расположение обратной связи перед формой;
- заголовок режима исправления, доступность только `fieldsToRevise` и переход к первому редактируемому полю.

Финальная проверка включает полный frontend test suite, backend test suite и сборку приложения.
