# Повторная проверка практики после `UNVERIFIED`

## Цель

Убрать тупиковое состояние практики после технического сбоя семантической
проверки. Пользователь должен иметь возможность повторно отправить сохранённую
попытку, при необходимости изменив только те поля, которые были доступны ему до
сбоя. Сервер не должен превращать технический сбой в выдуманную оценку или
ослаблять ограничения последней достоверной оценки.

## Текущее поведение и корневая причина

После ошибки ACP backend сохраняет попытку со статусом `UNVERIFIED`. Frontend
показывает сообщение «Сервер не стал выдумывать оценку», подписывает основную
кнопку как «Отправить исправление», но явно блокирует её. Дополнительная кнопка
«Проверить позже» показывает только toast и не отправляет запрос.

Существующий endpoint исправления принимает только родительскую попытку со
статусом `NEEDS_REVISION`. Редактор цикла также возвращает пустой список
доступных полей для `UNVERIFIED`. Поэтому клиент не может корректно обойти
блокировку: серверного контракта повторной проверки пока нет.

## Выбранный подход

Добавить отдельную операцию повторной проверки `UNVERIFIED`-попытки. Она
создаёт новую неизменяемую попытку и связывает её с предыдущей, поэтому история
сбоев и последующих результатов остаётся полной. Повторная оценка существующей
строки не используется: она потребовала бы удалить или заменить сохранённую
оценку и нарушила бы аудит.

Endpoint:

```text
POST /api/practice/attempts/{attemptId}/retries
```

Тело содержит доступные для изменения поля, выбранную модель и
`idempotencyKey`. Ответ и асинхронный жизненный цикл совпадают с обычной
отправкой попытки: `202 Accepted`, затем `EVALUATING` и один из терминальных
статусов.

## Область редактирования

Технический сбой не меняет область редактирования:

- если первичная попытка стала `UNVERIFIED`, доступны все поля `question`,
  `answer`, `reasoning` и `solution`;
- если проверка исправления стала `UNVERIFIED`, доступны только поля из
  `fieldsToRevise` ближайшей предшествующей достоверной попытки
  `NEEDS_REVISION`;
- если повторная проверка снова стала `UNVERIFIED`, та же область доступности
  наследуется через цепочку родителей;
- пользователь может изменить любое разрешённое поле или повторить проверку без
  изменений;
- изменение заблокированного поля отклоняется backend, даже если запрос создан
  не штатным frontend.

Backend вычисляет область редактирования по цепочке попыток. Для исходной
`UNVERIFIED`-попытки без родителя базой является первоначальный редактор со всеми
полями. Для потомка backend идёт по родителям до ближайшей попытки
`NEEDS_REVISION` и использует её `fieldsToRevise`. Цепочка, в которой невозможно
однозначно восстановить допустимые поля, отклоняется конфликтом вместо
расширения прав на редактирование.

## Backend

`PracticeAssessmentService` получает операцию retry, которая:

1. внутри транзакции вызывает существующий `lockOwner(ownerId)`, чтобы
   сериализовать конкурирующие retry-запросы пользователя;
2. ищет существующий результат по `idempotencyKey` и сразу возвращает его;
3. проверяет владельца, статус `UNVERIFIED` и то, что родитель остаётся последней
   попыткой своего assignment;
4. вычисляет унаследованную область редактирования;
5. берёт значения родителя для отсутствующих полей и проверяет изменения
   переданных полей по разрешённой области;
6. применяет обычную содержательную валидацию полного набора полей;
7. создаёт новую попытку с `parent_attempt_id` исходной `UNVERIFIED`-попытки;
8. запускает стандартную асинхронную оценку после фиксации транзакции.

Выбранную модель разрешено изменить. Если модель не передана, наследуется модель
родительской попытки. Повтор без изменений является допустимым, потому что цель
операции — восстановиться после технического сбоя, а не доказать наличие правки.

`PracticeCycleService` возвращает для последней `UNVERIFIED`-попытки редактор с
унаследованным списком `editableFields`. Сохранение черновика использует ту же
серверную функцию вычисления области и запрещает изменения остальных полей.

## Frontend

При `UNVERIFIED` форма снова становится рабочей в пределах серверного
`editor.editableFields`. Интерфейс показывает режим повторной проверки, а не
режим обычного исправления:

- заголовок объясняет, что предыдущая оценка не завершилась;
- перечисляются поля, которые можно изменить;
- submit-кнопка называется `Повторить проверку →` и активна;
- действие в панели обратной связи ведёт к форме и первому доступному полю;
- отправка вызывает retry endpoint последней `UNVERIFIED`-попытки;
- на время запроса сохраняется существующая защита `practiceSubmitting` от
  двойного submit;
- при ошибке запроса кнопка и унаследованная область редактирования
  восстанавливаются.

Для `NEEDS_REVISION`, `PASSED` и обычной первичной отправки текущее поведение не
меняется.

## Ошибки и конкуренция

- Retry попытки не в статусе `UNVERIFIED` возвращает `409 Conflict`.
- Чужая попытка остаётся неразличимой с отсутствующей и возвращает `404`.
- Повтор одного `idempotencyKey` возвращает уже созданную попытку.
- Создание retry сериализуется существующей блокировкой строки пользователя
  `lockOwner(ownerId)`. После появления потомка исходная попытка больше не
  является последней в assignment, поэтому повтор с другим ключом отклоняется
  `409 Conflict`. Повтор с тем же ключом возвращает созданного потомка до этой
  проверки.
- Сбой очередной оценки снова создаёт честный `UNVERIFIED`, не присваивая
  семантические баллы.

## Тестирование

Backend-регрессии проверяют:

- первичный `UNVERIFIED` разрешает изменить любое поле и создать новую попытку;
- `UNVERIFIED` после исправления наследует только исходные `fieldsToRevise`;
- повтор без изменений допустим;
- несколько последовательных `UNVERIFIED` сохраняют область редактирования;
- изменение недоступного поля отклоняется;
- новый attempt ссылается на предыдущий и сохраняет историю;
- idempotency возвращает одну попытку;
- retry запрещён для `EVALUATING`, `NEEDS_REVISION` и `PASSED`;
- другой пользователь не может повторить чужую попытку;
- черновик `UNVERIFIED` подчиняется той же области редактирования.

Frontend-регрессия проверяет, что `UNVERIFIED` разблокирует только серверные
`editableFields`, показывает `Повторить проверку` и действительно выполняет
`POST /practice/attempts/{id}/retries`. Отдельно проверяется восстановление
кнопки и полей после ошибки запроса.

## Критерии приёмки

1. После остановки подключения к coding agent пользователь видит честный
   `UNVERIFIED` и может повторно отправить попытку.
2. В DevTools появляется retry POST-запрос; отсутствие запроса при клике больше
   не воспроизводится.
3. Доступны ровно те поля, которые были доступны перед неудачной проверкой.
4. Повтор работает как с изменениями, так и без них.
5. История содержит отдельные исходную и повторную попытки.
6. Сервер отклоняет изменение любого недоступного поля.
7. Существующие сценарии первичной отправки, исправления и зачёта проходят без
   регрессий.
